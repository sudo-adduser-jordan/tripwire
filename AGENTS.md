## EVE SSO

- `ueberauth` 0.11 generates the OAuth `state`, keeps it in the signed `ueberauth.state_param` cookie, and exposes it as `conn.private[:ueberauth_state_param]` only during the request phase; `ueberauth_eve_online` 1.0.4 re-checks the callback state against that private value and falls back to the raw signed cookie, which never matches. `AuthController` therefore reseeds the private param from the verified cookie (`Ztripwire.SSO.state_param/1`) in a `:restore_state_param` plug before `plug Ueberauth`, keeping both CSRF checks working.
- Failures whose message key is `csrf_attack` or `invalid_state` flash "login session expired, sign in again" (the wide event still logs the raw keys and messages); a stale cookie only needs a browser retry. Other failures are trimmed to their first line and `@detail_limit` characters before they reach the flash or the log, because EVE answers a bad code with a full HTML error page that overflows the session cookie.
- Authorized ESI goes through `Ztripwire.ESI.valid_access_token/2`. It reads the SSO client id and secret from `Ztripwire.SSO.client_id/0` / `client_secret/0` (environment variables), not the `:ueberauth` app config, which stores `{:system, var}` tuples for Ueberauth to resolve; `refresh_access_token/1` needs the real values. Access tokens live in `Ztripwire.ESI.TokenCache`, a `:public` named ETS table because `put/2` and `delete/1` run from LiveViews and tracking pollers, and the rotated refresh token is written back to the character row so an app restart does not fall back to an already-rotated token. Refresh is serialized per character with `:global.trans/3` so a poller and a LiveView cannot both spend the rotating token, an authorized request that gets a 401 discards the cached access token and retries once, and a token endpoint `invalid_grant` clears the stored refresh token and returns `{:error, :reauth_required}`.
- Access tokens are verified at login by `Ztripwire.SSO.JWT.verify/2` before `Accounts.upsert_character_from_ueberauth/1`: it reads the JWKS from the SSO metadata (`https://login.eveonline.com/.well-known/oauth-authorization-server`, sent with the ESI user agent), checks the RSA signature with `jose` (`JOSE.JWT.verify_strict/3`), and validates `iss` (`https://login.eveonline.com` or `login.eveonline.com`), `aud` (`EVE Online` plus the configured client id), `exp` and the `CHARACTER:EVE:<id>` subject. The verifier pins `RS256`, requires a `kid` present in the key set, only follows a `jwks_uri` under `https://login.eveonline.com/`, caches the key set for an hour, and compares the token subject with the Ueberauth uid; `AuthController` rejects a callback whose `state` is missing or does not match the signed `ueberauth.state_param` cookie before `plug Ueberauth` runs. `ueberauth_eve_online` 1.0.4 only decodes the payload, so this is the signature check.
- The registered redirect URI is `http://localhost:4000/auth/evesso/callback`, so browse `localhost`, not `127.0.0.1`; set `EVESSO_CALLBACK_URL` to override the request-derived callback URL behind a proxy, which `config/runtime.exs` applies to the `evesso` provider and `config/prod.exs` reads with runtime plug initialization. Dev and prod share port 4000 but use different `secret_key_base` values (prod reads `PHX_SECRET_KEY_BASE`, which it requires; dev and test fall back to their own values), so a prod cookie is simply ignored by `task dev` instead of breaking the first login attempt.
- Session payloads go through `ZtripwireWeb.SessionUser`: `put/2` writes `%{"current_user" => %{"id" => eve_id, "name" => name}}` and merges `"character_ids"`, `get/1` also accepts legacy nested atom-keyed values, and `ids/1` feeds the topbar character list. LiveView receives `Plug.Conn.get_session/1` unchanged, so `DashboardLive.mount/3` must not pattern match atom-keyed nested maps — doing that silently fell back to the demo dashboard for logged-in users. Only anonymous visitors mount the demo; a session user whose character row is gone is redirected to `/` with a "Session expired" flash.
- Settings → Admin is gated on `is_admin`. `Accounts.admin_exists?/0` counts every admin except the legacy Demo User eve id (`Ztripwire.Demo.character_eve_id/0`), and when none exists a logged-in non-admin sees the claim modal on a hard dashboard load plus a persistent banner; the first "Make admin" press promotes the character through `Accounts.claim_admin/1` (later presses flash "An admin already exists"). The ESI CEO/Director/Ztripwire Admin grant at login is unchanged.

## ESI

- Every ESI request goes through `Ztripwire.ESI.Client` (`lib/ztripwire/esi/client.ex`), a GenServer that owns two public ETS tables. It sends `User-Agent` from `config :ztripwire, Ztripwire.ESI, :user_agent` (default `Ztripwire/0.1.0 (+https://bitbucket.org/daimian/tripwire)`, override with `ZTRIPWIRE_USER_AGENT`) and `X-Compatibility-Date` from `:compatibility_date` (default `2026-05-18`, override with `ZTRIPWIRE_ESI_COMPATIBILITY_DATE`), so a real contact address belongs in the deployed user agent.
- The same client is the response cache: entries are keyed by `{method, path, subject}` where subject is `:public` or a character eve id, TTLs come from `Cache-Control: max-age`/`x-client-cache-ttl` (with a 24-hour default for the static system/type/constellation/region routes), a stale entry is revalidated with `If-None-Match`, a `304` reuses the body, and `Client.expire/3`/`clear/0` exist for tests. Authorized bodies are never shared between characters.
- It is also the rate/error budget: responses record `X-Ratelimit-Group`, `X-Ratelimit-Remaining`, `X-Ratelimit-Limit`, `X-Esi-Error-Limit-Remain`, `X-Esi-Error-Limit-Reset` and `Retry-After`. A `429` blocks the route's rate-limit group until `Retry-After`, a `420` blocks globally until the error-limit reset, and a group at zero or an error limit at or below 5 skips the request and returns `{:error, {:rate_limited, seconds}}`/`{:error, :error_limit}`. `Req` is configured to retry only `408/500/502/503/504` (and transport timeouts), never `429`, so the budget owns that backoff.
- The tracking poller runs `/characters/{id}/online/` every 60 seconds and only follows `/location/` and `/ship/` every 10 seconds while that character is online **and** has a dashboard viewer (`Ztripwire.Tracking.Presence` keeps the viewer count; `DashboardLive` adds/removes one on mount/terminate). With no viewer it drops to the 5-minute idle online check, and with a dead refresh token or `invalid_grant` it idles until the next login updates the stored character. Every poller writes one ETS presence row (system, ship, online, character flags) with `updated_at`, which the topbar, occupant badges and the `refresh-occupants` path read instead of calling ESI per character; entries are deleted when the poller or `TestPresence` stops.
- `Ztripwire.Sde` reads `sde_systems`, `sde_constellations`, `sde_regions` and `sde_types` for names/security, so `Systems.fetch_info/2` and `Tracking.fetch_system_info/1` do not call ESI when the SDE tables are populated; `Systems.sde_info/1` is computed in the LiveView before the detail task starts, and `Systems.Catalog.find/1` resolves a name before `/universe/ids/`. The `:sde_enabled` application env (false in test) turns the reads off. The sovereignty map is `/sovereignty/map/` (the old `/universe/sovereignty/map/` path is a 404) and is cached for an hour.
- `SyncServer` refreshes corporation/alliance membership every **6 hours** by default (`:corp_sync_interval`) and `SyncServer.sync_character/1` refreshes one character immediately at login; the character/corp routes are revalidated with the shared ETag cache. `task setup`/`migrate`/`start`/`dev` run `mix ztripwire.sync_sde` after migrations.

## Map and signature sync

- Map data belongs to the mask, not to a map tab. `map_systems` and `map_connections` carry `mask_id`, so every tab of a mask reads and writes the same systems, connections, signatures and notes; pasting a scan once updates all tabs. The `maps` rows are views that keep only their name, home system and per-view node positions in `map_view_systems`; layout changes write only the active view's positions, and `list_chain_systems/2` overlays them on the shared systems before filtering by reachability from that view's home. `Mapping.delete_map_full/1` deletes a view (and resets the mask chain only when it is the last one), `delete_mask_chain/1` removes the shared chain, subscriptions use `Tracking.mask_topic/1`, and the migration `20261126000036_share_chain_per_mask` merges existing tabs by solar system, connection pair and signature id while keeping per-tab positions.

- Clicking a node body or its system name selects the system and patches `/<name>`; only the third, bottom line opens the editor, and it renders just when a wormhole signature matching the node's hole code exists: it carries `open-node-signature` in `MapLive`, which sends `{:open_node_signature, system_id, signature_id}` to `DashboardLive` to select the system and open that signature. A node whose hole has no scanned signature, and a root/home node with no hole at all, has no third line and is edited only from the signatures widget, and the map has no system editor any more: alias, class, favourite and placeholder renaming are not editable, and a placeholder is replaced by pointing a signature's **Leads** at the real system. The shelf straddles the node's bottom edge at `node_h - 8` and wraps into further rows 20 units down once a badge would pass `node_w - node_badge_inset/1` (`max(4, radius * 0.45)`, so 20 on the default oval node), so a system with six statics (Sentinel MZ, Thera) stays inside the 156 wide node.
- `MapLive` marks each system with tracked characters (from `Tracking.list_occupants/1`) using a `28x28` portrait badge on the node's top-right corner and an `r=8` count bubble when more than one character is there; with several occupants the badge switches to the unknown character portrait (`EveImages.unknown_character_portrait/1`, EVE character `1`) and the count bubble carries the total. Hovering the badge reveals an HTML tooltip inside a `<foreignObject>` (CSS `group`/`group-hover` only, no roundtrip, `pointer-events-none`), one row per occupant with the ship render (`EveImages.type_render/2`, type-icon then cube fallback), the square character portrait (same `rounded` treatment as the ship icon) and `Name - Ship`; the ship label prefers the character's `ship_type_name` carried over from the topbar presences (`DashboardLive.refresh_occupants/1` merges it into the occupant from `socket.assigns.presences`, and `{:topbar_loaded, data}` refreshes the occupants; the demo builds its occupant from the in-memory character instead of `Tracking.list_occupants/1`) and falls back to a trimmed `ship_name`, hiding ESI's `"/"` placeholder; the ship name is omitted when `ship_on_chain` is off. Its width is sized in map units to the longest `Name - Ship` row, clamped to 280–560, and it opens to the right of the node when it fits inside the map world (otherwise to the left); it opens below the node; it only flips above the badge when the tooltip would pass the bottom row *and* the node has room above, so a lone root node (no room above, nothing below) still opens downward. `list_occupants/1` therefore carries `ship_type_id`, which `Tracking.Poller` reads from the same `/characters/{id}/ship/` response as `ship_name`. Occupants are matched to the open map by the poller's last `solar_system_id` (not by the poller's own map id), so any character in a system the open chain contains is shown, and characters with `character_on_chain: false` are dropped. `DashboardLive.refresh_occupants/1` then scopes the list to the mask: a corporation mask keeps only characters whose `corporation_id` is the mask's `eve_owner_id`, an alliance mask the matching `alliance_id`, and personal/demo/custom masks keep every occupant. Every session character with a refresh token gets a poller on mount (`ensure_character_pollers/1`), so all of your characters report presence instead of just the one you logged in with; the tracker toggle in the signatures widget still turns a single character's poller off.

## Testing

- `mix test` covers contexts (`test/ztripwire/`), LiveViews (`test/web/live/`), and controllers (`test/web/controllers/`). Tests run inside the SQL sandbox against `priv/db/ztripwire-test.db` with a single pool connection (`pool_size: 1`), which keeps the LiveView processes and the serialized test transactions from racing on SQLite's writer lock.
- `config/test.exs` turns off `topbar_esi`, `pollers_enabled` and `sde_enabled`, silences sampled `Ztripwire.Log` info events, and routes every ESI request through `Ztripwire.ESIStub` (`req_options: [plug: Ztripwire.ESIStub]`); `esi_client_test.exs` overrides that with `Req.Test`, and `poller_test.exs` uses `Ztripwire.PollerESIStub` plus `start_supervised`. The two dashboard tracker tests opt back into real pollers with `Application.put_env(:ztripwire, :pollers_enabled, true)` and stop them in `on_exit`.
- Context tests build their own maps (`Ztripwire.TestFixtures.demo_mask/0` + `seed_demo_map/1` insert the `Ztripwire.Demo` fixture into SQLite: the 27-system chain with signatures and notes, including two scanned-but-unmapped leaf holes that end in empty unknown nodes; the demo paste lives in a comment on the Jita system). `test/ztripwire/demo_test.exs` covers the in-memory fixture and edits, and `test/web/live/demo_no_db_test.exs` attaches to `[:ztripwire, :repo, :query]` and asserts the demo dashboard performs no repository queries.
- Dashboard LiveView tests drive the widgets (signature paste, stale toast, chain map rendering, settings tabs) through `ZtripwireWeb.LiveComponents` events; select systems via `#system-container button[title='Select system …']`.
- The upstream reference (daimian/tripwire, PHP) ships no test suite. Its maintained fork's suites (mocha `app/js-test`, Playwright `e2e/`, `tests/php/note-html.test.php`) are the comparison baseline; behaviors already ported: signature paste parsing, wormhole eligibility and rendering, automapper jump labeling, mask kinds, note sanitization (as markdown escaping), and stat counters. Known upstream gaps not present in this port: faction-warfare conditional gates, mass dialog parsing, Drifter/C13–C18 generic system types, EVE-Scout Thera link supplier, and client-side pathfinding (routes come from ESI here).

## Logging

- `Ztripwire.Log.new/1` builds a wide event (`timestamp`, `service`, `node`, `pid` merged with caller fields); `put/3` and `merge/2` enrich it.
- `Ztripwire.Log.emit/2` accepts `:debug | :info | :warning | :error` with a map or binary message, appends one JSON object per line to `logs/test/YYYY-MM-DD.jsonl` (debug, info) or `logs/errors/YYYY-MM-DD.jsonl` (warning, error), then pretty prints a colored line to stdout.
- `Ztripwire.Log.keep?/2` always keeps errors, warnings, events carrying an `error` field, and events with `duration_ms > 2000`; the rest sample at the configured `sample_rate`.
- Every ESI response emits an `esi_request` event (`method`, `path`, `status`, `duration_ms`, `cached`, `group`, `remaining`, `error_limit_remain`) at `info`, or `warning` for `401/403/420/429/5xx`; transport failures emit `esi_request_failed`, poller failures emit `esi_poll_failed`, and login emits `sso_token_invalid` when `SSO.JWT` rejects a token.
- Config (`config/config.exs`, `config :ztripwire, Ztripwire.Log`): `service`, `sample_rate`, `test_path`, `error_path`.
- `ZtripwireWeb.Plugs.WideEvent` (`web/plugs/wide_event.ex`) runs after `Plug.RequestId` in `ZtripwireWeb.Endpoint`, seeds the event (request_id, method, path, remote_ip, user_agent), and emits status, `duration_ms`, and outcome on `register_before_send`.
- Tests: `test/ztripwire/log_test.exs` redirects paths to a tmp dir via `Application.put_env(:ztripwire, Ztripwire.Log, ...)` and restores afterwards.

## Task Automation

`Taskfile.yml` (Task v3, `silent: true`, `output: group`, `set: [errexit, nounset, pipefail]`, `dotenv: [.env]`). Server lifecycle tasks run inline shell commands; the detached production server logs to `logs/prod.log` and its pid lives only in the launching shell variable, so no pid file is written; other tasks print colored `[name]` prefixes before commands.

| Task | Runs |
|---|---|
| `task install` | `mix deps.get`, `mix assets.setup`, `npm ci --prefix assets` |
| `task update` | `mix deps.update --all`, `npm update --prefix assets` |
| `task remove` | `rm -rf _build deps assets/node_modules priv/static/assets cover` |
| `task setup` | `mkdir -p priv/sde logs/test logs/errors`, `curl` official JSONL SDE to `priv/sde/eve-online-static-data-latest-jsonl.zip` with ETag conditional fetch, `mix ztripwire.build_wormhole_systems`, `mix deps.get`, `mix ecto.setup`, `mix ztripwire.sync_sde`, `mix assets.setup`, `mix assets.build` |
| `task migrate` | `mix ecto.migrate` + `mix ztripwire.backfill_system_data`, `MIX_ENV=test mix ecto.migrate`, `MIX_ENV=prod` variants |
| `task start` | `task stop`, `mkdir -p logs priv/sde`, `curl` official JSONL SDE with ETag conditional fetch, prod migrations plus `mix ztripwire.backfill_system_data` and `mix ztripwire.sync_sde`, assets, then launch detached with `DATABASE_PATH` defaulting to `./priv/db/ztripwire-prod.db` and keep the `$!` pid in the same shell; block until `logs/prod.log` reports a running endpoint, then print the URL (fails with the log tail if the server dies while booting) |
| `task stop` | `pgrep -f "mi[x] phx\.server"` kills each server process group with `TERM`, waits for it to disappear, sweeps with `pkill`, then waits for the port to be released |
| `task dev` | `task stop`, `mkdir -p logs/test logs/errors priv/sde`, `curl` official JSONL SDE with ETag conditional fetch, `mix ecto.migrate`, `mix ztripwire.sync_sde`, then `MIX_ENV=dev mix phx.server` attached on port `PORT` (default `4000`) with live reload and the `config/dev.exs` watchers; Ctrl-C stops it |
| `task diagram` | `mkdir -p docs`, then `mix ztripwire.diagrams`, which writes `docs/db-schema.md` and `docs/architecture.md` |

Server lifecycle blocks run under `sh -c` because Task's built-in shell does not implement `$!` or `kill`.

Dev starts the Erlang `:os_mon` application (`mix.exs` `extra_applications` for `MIX_ENV=dev` only), so the LiveDashboard mounted at `/dev/dashboard` serves the OS Data page at `/dev/dashboard/os_mon`. The same dashboard's Ecto Stats page is backed by the dev-only `ecto_sqlite3_extras` dependency and an explicit `ecto_repos: [Ztripwire.Repo]` route option, and reports total/table/index size, sequence numbers, PRAGMA and compile options, and integrity checks for `priv/db/ztripwire-dev.db`.

## Conventions

- No `#` comments in Elixir, Taskfile, or other source files; `#{...}` interpolation inside strings is not a comment. Document in `README.md` or this file instead.
- Tests run with `mix test`; single file with `mix test <path>`. Log tests must not write to real `./logs/`.
- Commits use `tag: statement of change` with one of `add`, `update`, `remove`, `move`, `feature`, `fix`, no body, on the current branch, without pushing.
